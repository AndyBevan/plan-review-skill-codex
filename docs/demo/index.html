Key Patterns & Decisions

Single-file review artifact

What: Generate a single `_plan-review/index.html` file with tabs for every applicable artifact type.

Why: Keeps review friction low and makes local file opening straightforward.

In practice: Navigation, mockup subviews, diagrams, and concerns all live in one browser-viewable page.

Review-before-build workflow

What: Stay in review mode until the user approves the generated artifact.

Why: It is cheaper to fix architecture, UI expectations, or data-model mistakes before implementation starts.

In practice: Feedback updates the review artifact instead of jumping to production code immediately.

Dense developer presentation

What: Use compact layouts, tight tables, and information-dense cards.

Why: The artifact is meant to guide implementation, not act as a stakeholder slide deck.

In practice: Data models emphasize fields, constraints, indexes, and lifecycle flows over decorative styling.

Plan Concerns

Review these before implementation starts.

3 of 6 reviewed
#1Critical

State persistence strategy needs stable identifiers

If concern state is keyed by list order instead of concern id, reviewed markers will drift whenever the generated page changes ordering.

#2Important

Mermaid rendering in hidden tabs can fail silently

The skill must either rerun Mermaid on tab activation or avoid `display: none` for hidden Mermaid containers.

#3Consider

Concern language should stay actionable

Vague observations are harder to resolve than a concise risk paired with a suggested mitigation.

#4Important

Architecture cards need rationale, not just labels

A folder tree alone will not help users challenge structural decisions before implementation.

#5Consider

Mockups should stay grounded in the plan

Inventing extra features weakens trust in the artifact and can blur scope boundaries.

#6Important

Indexes should reflect implied query paths

Board views, comment timelines, and membership lookups need explicit indexes in the review artifact, not just entity fields.
